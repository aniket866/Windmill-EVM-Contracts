### Finding 1: Committed `.env` contains a live private key and API key — `.env:2-5`

- Severity: Critical
- Confidence: 0.95
- Category: secrets_exposure
- Description: The repository tracks a `.env` file containing `PRIVATE_KEY=0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80` (Anvil account #0 default private key) and an active `ETHERSCAN_API_KEY=2XXGKFWGEA4Q4JAG3BD188YIIZTQ4J4PY5`. Tracking `.env` files in git creates severe operational exposure: contributors may replace placeholder values with funded production keys and inadvertently commit them. The Etherscan key is already exposed in repository history.
- Exploit Scenario: A team member or external contributor updates `.env` with a real deployer key on Sepolia/Mainnet, runs `git commit -a`, and pushes upstream. Public scrapers detect the commit and immediately sweep all funds associated with the key.
- Recommendation:
  1. Untrack the file immediately: `git rm --cached .env`.
  2. Confirm `.gitignore` ignores `.env` (it does).
  3. Rotate the compromised Etherscan API key on etherscan.io.
  4. Ensure CI rejects any PR or commit containing `.env`.

### Finding 2: `matchOrdersBatch` reverts entire batch on early full fill due to missing loop break — `WindmillExchange.sol:275-346`

- Severity: High
- Confidence: 0.90
- Category: denial_of_service / logic_error
- Description: In `matchOrdersBatch`, a primary `orderId` is iteratively matched against multiple `counterOrderIds`. If `orderId` is fully filled during iteration `i` (where `i < counterOrderIds.length - 1`), the contract deactivates the order via `_deactivateOrder(orderId)`. However, the loop does not terminate with `break`. On the subsequent iteration `i + 1`, `_getOrderMem(orderId)` retrieves the deactivated order, and `_validateMatch` executes:
  ```solidity
  if (!buy.active) revert OrderInactive();
  if (!sell.active) revert OrderInactive();
  ```
  This immediately reverts the transaction with `OrderInactive()`, undoing all preceding matches executed in the batch.
- Exploit Scenario: A keeper detects an opportunity to match a 1000-unit buy order against three sell orders of 400, 600, and 300 units. The keeper submits `matchOrdersBatch(buyId, [sell1, sell2, sell3], deadline)`. Matches 1 and 2 completely satisfy the 1000-unit buy order. Iteration 3 attempts to validate the now-inactive `buyId`, causing the entire transaction to revert. The keeper loses execution gas, and no trades settle.
- Recommendation: After settlement in `matchOrdersBatch`, inspect whether the primary order is fully filled. If it is filled, break out of the loop immediately:
  ```solidity
  if (order.isBuy ? buyFilled : sellFilled) {
      break;
  }
  ```

### Finding 3: Forced WETH unwrapping & native ETH push enables griefing DoS against keepers — `WindmillExchange.sol:99-107`, `255-259`

- Severity: High
- Confidence: 0.85
- Category: denial_of_service
- Description: Whenever `token == WETH`, `_safeTransferTokenOrETH` automatically unwraps WETH by calling `IWETH(WETH).withdraw(amount)` and transfers native ETH via low-level `.call{ value: amount }("")`. If the recipient (`sell.maker`, `keeper`, or `treasury`) is a smart contract that does not implement `receive() external payable`, consumes more than the 2300 gas stipend (if called via transfer/send) or explicitly reverts, `to.call` fails and reverts with `EthTransferFailed()`.
- Exploit Scenario:
  1. A malicious actor deploys a contract with no `receive()` or a reverting `fallback()`.
  2. The attacker creates a sell order where `tokenOut == WETH`.
  3. When an autonomous keeper bot attempts to execute `matchOrders`, `_safeTransferTokenOrETH` attempts to transfer native ETH to the attacker's contract.
  4. The call reverts with `EthTransferFailed()`. The order cannot be matched, and the keeper bot repeatedly fails and burns transaction fees attempting to execute against phantom liquidity.
  5. Furthermore, if the protocol `treasury` contract is upgraded to a smart contract without a payable receiver, all matches involving WETH with non-zero protocol fees will revert.
- Recommendation:
  - Do not unconditionally unwrap WETH into native ETH on settlements. Settle in standard ERC-20 WETH, and allow users/keepers to opt into unwrapping, or use an escrow/pull-withdrawal mechanism.
  - At minimum, ensure `treasury` and `keeper` rewards are sent as ERC-20 WETH rather than raw ETH.

### Finding 4: Keeper and protocol fee underflow risk if cap is raised — `WindmillExchange.sol:252-256`, `331-336`

- Severity: Medium
- Confidence: 0.85
- Category: arithmetic
- Description: In `matchOrders` and `matchOrdersBatch`, settlement sends the seller:
  ```solidity
  _safeTransferTokenOrETH(buy.tokenIn, sell.maker, notionalAmount - keeperFee - protocolFee);
  ```
  The contract does not validate that `keeperFee + protocolFee <= notionalAmount`. Under current constants (`keeperFee = 0.1%` and `protocolFeeBps <= 500` / 5%), total fees equal 5.1%, which cannot exceed 100% for standard trades. However, lacking an explicit validation check means any future parameter adjustment (or governance upgrade modifying the cap) could cause silent arithmetic underflows (reverts in Solidity 0.8+).
- Exploit Scenario: Governance raises fee caps or updates fee models in a future release. A keeper executes a match where fees exceed notional value; the subtraction underflows and reverts, permanently breaking trade execution for that pair until governance intervenes.
- Recommendation: Add an explicit assertion before transfers:
  ```solidity
  uint256 totalFees = keeperFee + protocolFee;
  if (totalFees > notionalAmount) revert InvalidProtocolFee();
  _safeTransferTokenOrETH(buy.tokenIn, sell.maker, notionalAmount - totalFees);
  ```

### Finding 5: Division rounding truncation creates unmatchable dust orders locking maker capital — `WindmillExchange.sol:425-434`

- Severity: Medium
- Confidence: 0.80
- Category: arithmetic / stuck_funds
- Description: In `_computeSettlement`:
  ```solidity
  notionalAmount = MathUtils.mulDiv(executedQuantity, MathUtils.RAY, settlementPrice);
  executedQuantity = MathUtils.mulDiv(notionalAmount, settlementPrice, MathUtils.RAY);
  if (executedQuantity == 0) revert ZeroAmount();
  buyFilled = (buy.remainingIn - notionalAmount) == 0;
  sellFilled = (sell.remainingIn - executedQuantity) == 0;
  ```
  When integer division floors `notionalAmount`, recomputing `executedQuantity` can yield a value 1 wei smaller than `sell.remainingIn`. As a result, `sellFilled` is `false`, and `_updateRemainingIn` stores `remainingIn = 1` in storage. Any subsequent attempt by a keeper to match this remaining 1-wei dust order calculates `notionalAmount = 0` (whenever `settlementPrice > RAY`), producing `executedQuantity = 0`, which reverts with `ZeroAmount()`.
- Exploit Scenario: A user places a large sell order. A match consumes 99.999999% of the order, but due to floor division, 1 wei remains in the contract. Keepers identify the active order and repeatedly attempt matches, all of which revert with `ZeroAmount()`. The user's residual balance remains trapped in the order until manually cancelled.
- Recommendation: If the remaining balance after a trade is below a minimum threshold (dust tolerance, e.g., 100 wei) or results in `executedQuantity == 0`, consider the order filled or allow a clean closeout.

### Finding 6: Cross-contract reentrancy surface via WETH `withdraw()` and ETH forwarding — `WindmillExchange.sol:99-107`

- Severity: Medium
- Confidence: 0.75
- Category: reentrancy
- Description: `_safeTransferTokenOrETH` transfers native ETH to untrusted external addresses during settlement and cancellations. All state updates in `WindmillExchange` occur before external transfers (CEI), and external mutating entry points are guarded by OpenZeppelin's `nonReentrant`. However, during execution of the external call, the recipient receives control. If the recipient queries view functions (such as `getOrdersByPair`) or calls into other DeFi protocols that integrate with the exchange, the exchange is in an intermediate state where order arrays have been modified while subsequent transfers in the loop are still pending.
- Exploit Scenario: A smart contract maker receives ETH in `receive()`. In that callback, it interacts with a lending protocol or liquidity pool that relies on `WindmillExchange.getOrdersByPair()` to calculate orderbook depth, exploiting temporary discrepancies before all settlements in a batch finish.
- Recommendation: Adopt a pull-over-push withdrawal pattern for ETH, or maintain strict separation between internal settlement accounting and external token disbursements.

### Finding 7: Single-step ownership transfer risk — `WindmillExchange.sol:92-97`

- Severity: Medium
- Confidence: 0.80
- Category: access_control
- Description: `transferOwnership` directly updates the `owner` state variable in a single transaction without verifying that the destination address is capable of receiving ownership. If the owner mistakenly inputs an invalid address, zero address checks catch address(0), but typos or unsupported smart contracts result in irrevocable loss of administrative control.
- Exploit Scenario: An administrator copies an address from a clipboard that contains a typo. The function executes, immediately granting ownership to an unrecoverable address. Critical functions like `pause`, `unpause`, and `setProtocolFee` can never be invoked again.
- Recommendation: Implement a two-step ownership pattern (such as OpenZeppelin's `Ownable2Step`), where the prospective owner must call `acceptOwnership()` before ownership transfers.

### Finding 8: Unbounded loop and duplicated settlement logic in `matchOrdersBatch` — `WindmillExchange.sol:265-347`

- Severity: Low
- Confidence: 0.80
- Category: code_quality / denial_of_service
- Description: `matchOrdersBatch` accepts an arbitrary-length array `counterOrderIds` without pagination or size capping. Submitting a large batch can exceed the Ethereum block gas limit (30M gas). Additionally, lines 300–342 in `matchOrdersBatch` duplicate the exact fee calculation and settlement logic from `matchOrders` (lines 222–260), introducing maintenance risks where bug fixes applied to one function are omitted in the other.
- Exploit Scenario: A keeper attempts to settle 100 matches in one batch. Gas consumption exceeds block limits, causing all transactions to fail. In parallel, future developers fix an accounting issue in `matchOrders` but overlook `matchOrdersBatch`, leaving an exploitable discrepancy.
- Recommendation:
  - Enforce a `MAX_BATCH_SIZE` check (e.g., `require(counterOrderIds.length <= 50, "Batch too large")`).
  - Refactor settlement logic into a private `_settlePair(Order memory buy, Order memory sell)` helper reused by both entry points.

### Finding 9: Memory expansion DoS in `getOrdersByPair` pagination — `PairStorage.sol:36-42`, `WindmillExchange.sol:362-388`

- Severity: Low
- Confidence: 0.75
- Category: denial_of_service
- Description: `getOrdersByPair` supports pagination via `cursor` and `limit`. However, it first calls `_getOrdersByPair(tokenA, tokenB)`, which copies the entire dynamic array `_pairOrders[key]` from storage into memory:
  ```solidity
  function _getOrdersByPair(address tokenA, address tokenB) internal view returns (uint256[] memory) {
      return _pairOrders[pairKeyOf(tokenA, tokenB)];
  }
  ```
  In EVM execution, memory expansion costs grow quadratically. Once a pair accumulates tens of thousands of historical or active orders, copying the full array into memory will cause `getOrdersByPair` to revert due to out-of-gas, even if the caller only requested a `limit` of 10 items.
- Exploit Scenario: An active pair accumulates 20,000 orders over time. A keeper or UI calls `getOrdersByPair(tokenA, tokenB, 0, 10)`. The RPC call runs out of gas attempting to expand memory for the full 20,000 array entries, blinding keepers from indexing active orders.
- Recommendation: Read items directly from storage using index bounds rather than copying the entire array into memory:
  ```solidity
  uint256 total = _pairOrders[key].length;
  // iterate directly from storage to populate the fixed-size page
  ```

### Finding 10: `cancelOrder` exposes WETH unwrap path during emergency pause — `WindmillExchange.sol:189`

- Severity: Low
- Confidence: 0.70
- Category: access_control
- Description: `cancelOrder` is intentionally omitted from the `whenNotPaused` modifier to guarantee users can retrieve escrowed funds during an administrative pause. However, when `order.tokenIn == WETH`, `cancelOrder` invokes `IWETH(WETH).withdraw()` and sends native ETH. If the exchange was paused due to a compromise in WETH interactions or reentrancy vectors, `cancelOrder` still triggers the vulnerable execution path.
- Exploit Scenario: A vulnerability is detected in native ETH handling. The admin pauses the contract to protect funds. An attacker exploits the remaining un-paused `cancelOrder` path to trigger the vulnerable interaction.
- Recommendation: Provide an emergency withdrawal mode during pause that returns raw ERC-20 WETH without attempting native ETH unwrapping.

### Finding 11: Missing token decimal normalization between heterogeneous pairs — `WindmillExchange.sol:419-428`

- Severity: Low
- Confidence: 0.75
- Category: decimal_handling
- Description: `MathUtils.RAY` (`1e27`) is used uniformly across price and settlement calculations. However, ERC-20 tokens exhibit diverse decimals (e.g. USDC with 6 decimals, WBTC with 8 decimals, WETH with 18 decimals). The contract performs no decimal normalization:
  ```solidity
  buyerAffordableQuantity = MathUtils.mulDiv(buy.remainingIn, settlementPrice, MathUtils.RAY);
  ```
  If `tokenIn` is USDC (6 decimals) and `tokenOut` is WETH (18 decimals), `buy.remainingIn` is denominated in `1e6`, while `buyerAffordableQuantity` must match WETH's `1e18`. To achieve parity, the `settlementPrice` must be scaled by an unnatural `1e39` factor. If users or keepers submit prices assuming conventional 18- or 27-decimal representations, settlement will execute orders at distorted ratios.
- Exploit Scenario: A user places a limit order using a standard 18-decimal price quote for a USDC/WETH pair. The exchange interprets the quote directly without decimal scaling, causing the order to fill at an unintended valuation.
- Recommendation: Introduce explicit token decimal normalization (scaling amounts to a common 18- or 27-decimal precision base before calculating prices) or strictly document and enforce decimal-adjusted quote formatting in client interfaces and keeper specifications.

## Notes

### Note 1: Single-admin ownership model without timelock — `WindmillExchange.sol:43-55`

- Category: accepted-risk
- Observation: The `owner` address holds unilateral administrative powers to pause/unpause the exchange, adjust protocol fees up to 5%, set the protocol treasury, and transfer ownership without a timelock or multisig delay.
- Rationale: Project documentation (`AGENTS.md`, `CONTRIBUTING.md`) confirms this is an intended design for the current alpha stage of Windmill Exchange to allow rapid incident response. The hardcoded 500 bps (5%) cap provides a ceiling on fee manipulation.

### Note 2: Compile-time hardcoded keeper fee — `WindmillExchange.sol:252`

- Category: design-tradeoff
- Observation: The keeper fee is set to a constant `notionalAmount / 1000` (0.1%). It cannot be calibrated by the owner or adjusted for volatile gas environments.
- Rationale: Hardcoding keeper fees prevents admin front-running or keeper fee extraction attacks, keeping protocol mechanics deterministic.

### Note 3: Empty payable `receive()` without administrative fund rescue — `WindmillExchange.sol:68`

- Category: design-tradeoff
- Observation: The contract defines an empty `receive() external payable {}` function to accept ETH from WETH withdrawals. Any ETH sent directly to the contract outside of order creation or WETH unwrapping is permanently locked, as no rescue function exists.
- Rationale: Omitting arbitrary ERC-20 / ETH sweep functions prevents admin rug-pull vectors against user escrow balances.

### Note 4: Explicit scope boundary excluding off-chain components

- Category: scope-definition
- Observation: The subdirectories `Windmill-EVM-Keeper2/` and `Windmill-EVM-WebUI/` exist in the workspace but were intentionally excluded from this review.
- Rationale: The review was explicitly scoped to the EVM smart contracts repository only.

## Limitations

**Standing limitations:**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations:**

- The `Windmill-EVM-Keeper2/` and `Windmill-EVM-WebUI/` repositories were explicitly excluded from this audit per user instructions; off-chain interactions, bot strategies, and frontend signing hazards were not analyzed.
- Formal verification of the assembly 512-bit math in `MathUtils.mulDiv` was not performed; review was based on structural equivalence with the verified Bloemen-Charley algorithm.
- No live on-chain deployment state on Sepolia was queried; all findings are based strictly on repository source code.
